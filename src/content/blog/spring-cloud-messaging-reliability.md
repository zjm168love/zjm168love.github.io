消息中间件"能用"和"可靠"之间隔着不少细节。这里记几条在 Spring Cloud + RabbitMQ 场景里反复验证过的实践。

**生产端**：开启 publisher confirm，把"消息是否到达 broker"变成可确认的事实，而不是默认成功。发送失败要有补偿（重试或落库重发）。

**消费端**：手动 ack，处理成功才确认；处理失败进重试队列，超过次数进死信，避免消息悄悄丢失或无限重投。

**幂等**：消费方必须幂等。网络重试、重复投递是常态，用业务唯一键去重比指望"只投一次"现实得多。

**顺序**：真正需要全局顺序的场景很少。多数业务只需要"同一业务键内有序"，用分区/路由键收敛即可，别为全局顺序牺牲吞吐。

可靠性不是某个开关，而是生产确认 + 消费幂等 + 死信兜底这套组合拳。缺任何一环，故障时都会丢消息或重复处理。
